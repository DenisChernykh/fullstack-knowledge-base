# REST и моделирование ресурсов

## Вопрос

Что делает API RESTful, чем REST отличается от самого HTTP и как моделировать ресурсы?

## Короткий ответ

REST — архитектурный стиль, а HTTP — протокол. RESTful API использует единообразный интерфейс: ресурсы имеют устойчивые URI, операции выражаются семантикой HTTP-методов, сообщения самодостаточны, сервер не хранит состояние клиентской сессии между запросами, а ответы могут явно описывать кэширование. Не любой JSON over HTTP является REST. Например, POST /runReport — HTTP API, но ресурсная модель POST /reports с последующим GET /reports/{id} лучше выражает создание и жизненный цикл отчёта. При этом RPC-команда не является ошибкой, если она честнее описывает бизнес-операцию.

## Разбор

- Сначала ищут существительное и жизненный цикл: заказ, отчёт, импорт, пользователь. URI идентифицирует ресурс, а не конкретный метод контроллера.
- GET читает представление, POST создаёт подчинённый ресурс или запускает явно неидемпотентную операцию, PUT заменяет состояние по известному URI, PATCH меняет часть состояния, DELETE удаляет.
- REST не требует конкретного JSON-формата и не запрещает асинхронные операции. Для долгой работы можно создать operation resource и возвращать 202 с URI статуса.
- Если предметная область действительно командная, RPC endpoint допустим. Важнее последовательный контракт, ошибки, идемпотентность и наблюдаемость, чем формальная «чистота» URL.

## Частые уточнения

**Чем REST отличается от CRUD?** CRUD — набор операций над данными, REST — ограничения взаимодействия. Один ресурс может поддерживать не все CRUD-операции, а бизнес-команда может создавать новый ресурс результата.

**Обязан ли REST API использовать JSON?** Нет. REST не задаёт формат представления; это может быть JSON, XML, HTML или другой media type.

**Когда RPC понятнее ресурса?** Когда операция не имеет естественного жизненного цикла ресурса и искусственное существительное только скрывает смысл команды.

## Где ошибаются

Нельзя определять REST как «JSON плюс правильные глаголы» или считать любой endpoint с существительным RESTful. Также не стоит переделывать ясную бизнес-команду в странный псевдоресурс только ради догмы.
